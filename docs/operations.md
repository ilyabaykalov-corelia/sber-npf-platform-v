# Упаковка, проверка и установка

Команды выполняются из корня sber-npf-platform-v. Для упаковки нужны Bash и Python 3.

## Упаковка

```bash
bash scripts/package-platform-v.sh
# Отдельный выходной файл:
bash scripts/package-platform-v.sh /tmp/sber-npf-platform-v-check.zip
```

Скрипт читает .info.meta.json, проверяет допустимость путей и наличие файлов, исключает дубликаты и пишет ZIP через временный файл с последующим os.replace. В архив попадают манифест и перечисленные файлы. Markdown, .env, dist и соседние исходники не добавляются автоматически.

Проверяется состав файлов, но не семантика XML, GraphQL или BPMN. Успешная упаковка не равна успешной публикации модели.

## Проверки при изменениях

1. Проверить синтаксис изменённых JSON/XML/BPMN и наличие всех файлов из манифеста.
2. Сверить DocumentType и DocumentProcessSettings с реестром Corelia и ID процессов в BPMN.
3. Для изменения модели проверить parent/mappedBy, уникальность documentId, document/version и commandKey, ожидаемые типы и длины.
4. Сверить полные GraphQL-тела в permissions с ресурсами ядра, BPMN и независимой фикстурой.
5. При изменении контракта запустить `bash ../corelia/scripts/test.sh`; при затронутом клиенте — `npm --prefix ../sber-npf-react run build`.
6. Собрать архив и проверить его содержимое. На согласованном тестовом стенде отдельно подтвердить принятие модели, реальное исполнение permissions и процессы обоих видов.

PlatformStub не заменяет SDK-генератор и BPM-движок. Отдельного scripts/validate-document-model.py в текущем репозитории нет.

## Установка совместимого комплекта

Перед установкой определить текущую модель, совместимость данных и запущенных процессов. Автоматического сценария миграции и обязательного сброса данных в комплекте нет. Сброс не является стандартным шагом обновления.

Опубликовать согласованные модель, права, разрешённые операции, оба справочника и оба процесса средствами целевого стенда. Затем использовать совместимые Corelia и React. Конкретная процедура публикации зависит от установленного дистрибутива и здесь не подтверждается локальной упаковкой.

Проверить создание ПДС и КИД ОПС, обязательный первый файл, v1, редактирование и историю состава, сохранение того же процесса, конфликт и повтор команд, переход КИД ОПС в STORED и запрет изменений после него.

## Справочники

DocumentType и DocumentProcessSettings публикуются GraphQL-запросами через конструктор Platform V.
Сразу после публикации модели выполните
[`../bootstrap-document-types.graphql`](../bootstrap-document-types.graphql) от имени `app_owner`.
Выполните зарегистрированную операцию `upsertDocumentType` отдельно для `PDS_CONTRACT`
и `KID_OPS`, передав `id` и `name` через variables. До этого шага создание документа невозможно: поле
`Document.documentType` — внешний ключ на `DocumentType`.

## LCUI и диагностика

LCUI продолжает ссылаться на старый BFF и маршруты ПДС. Не считать его настройку готовой для Corelia gateway; согласовать назначение этих импортируемых файлов с потребителями перед изменением.

При ошибке GraphQL проверять operationName, полное тело, параметры, права пользователя и соответствие опубликованной модели. При ошибке запуска — DocumentProcessSettings, enabled, публикацию processId и инцидент BPM. При таймауте смотреть конкретный внешний вызов и логи платформы; не повторять создание вслепую.
